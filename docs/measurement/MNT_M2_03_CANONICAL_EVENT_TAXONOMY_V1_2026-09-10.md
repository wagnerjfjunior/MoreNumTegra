## 1. Purpose

Define the stable, project-owned semantic event vocabulary for MoreNumTegra before GA4, Google Ads or Meta business-event implementation is expanded.

The taxonomy is vendor-neutral at the source layer. Application/runtime semantics are emitted once into the project data layer and later mapped by GTM to authorized destinations.

Preserve:

```text
SOURCE EVENT SEMANTICS != DESTINATION EVENT NAME
EVENT DEFINED != EVENT IMPLEMENTED
EVENT IMPLEMENTED != CONVERSION
CTA CLICK != LEAD
FORM SUBMIT ATTEMPT != LEAD
GREEN /page/view != PROJECT PAGE EVENT
YOUTUBE TELEMETRY != PROJECT EVENT
```

Primary/secondary conversion classification belongs to `MNT-M2-04`. GA4 administrative ownership belongs to `MNT-M2-05`; Meta ownership belongs to `MNT-M2-06`; runtime implementation belongs to `MNT-M2-09`; end-to-end proof belongs to `MNT-M2-10`.

## 2. Source-event naming contract

All project-owned semantic source events use:

- lowercase `snake_case`;
- prefix `mnt_`;
- stable semantic names independent of UI copy, locale, campaign or vendor;
- no project/development/filter value embedded dynamically in the event name;
- schema version `1` for this taxonomy.

Canonical v1 source events:

```text
mnt_page_view
mnt_section_click
mnt_catalog_filter
mnt_catalog_search
mnt_intent
mnt_form_start
mnt_form_submit_attempt
mnt_lead_success
```

No additional event name is canonical unless a later governed taxonomy revision adds it.

## 3. Common event envelope

Every implemented project semantic event MUST carry the following project envelope unless a later technical constraint is explicitly adjudicated:

| Field | Required | Semantics |
|---|---|---|
| `event` | YES | canonical source event name |
| `mnt_event_id` | YES | one project correlation identity per semantic occurrence, per MNT-M2-02 |
| `mnt_event_version` | YES | integer `1` for this taxonomy |
| `page_identity` | YES | `moretegra_home` for the current V1 home |
| `route` | YES | `/` for the current V1 home |
| `funnel_stage` | YES | allowlisted stage defined below |
| `placement` | WHEN_APPLICABLE | stable component/placement enum, never free-form UI text |

Project-context fields are added only when the event is associated with a specific development/offer:

| Field | Required | Semantics |
|---|---|---|
| `project_name` | WHEN_PROJECT_CONTEXT_EXISTS | canonical development identity from `project.projectName || project.name` |
| `offer_name` | WHEN_PROJECT_CONTEXT_EXISTS | exact offer/card identity from `project.name` |

Do not invent a slug or synthetic product ID merely for Measurement. A future governed product registry may add a stable identifier; until then, the canonical project and offer names already present in the project data model are the identity source.

## 4. Funnel-stage enum

Canonical funnel stages for v1:

```text
discovery
consideration
intent
lead
```

Rules:

- `discovery` = page/catalog discovery state;
- `consideration` = explicit content/filter/search interaction that refines evaluation;
- `intent` = explicit request/contact/form action short of verified lead success;
- `lead` = only a verified Green Form 46 success occurrence.

`funnel_stage` is descriptive taxonomy. It is not a conversion classification and must not bypass MNT-M2-04.

## 5. Event definitions

### 5.1 `mnt_page_view`

Semantic definition:

> One project-owned eligible view of the canonical MoreNumTegra document.

Trigger contract:

- only on `moretegra.com.br`;
- exactly once per eligible canonical browser document load;
- a legitimate reload is a new occurrence;
- no project page event on `www.moretegra.com.br`;
- never generated by observing or forwarding Green `/page/view`.

Required event values:

```text
funnel_stage = discovery
placement = document
```

Dedup rule:

`MAX_PROJECT_PAGE_VIEW_PER_DOCUMENT_LOAD = 1`.

MNT-M2-09 must choose one GA4 page-view implementation path and prevent automatic + manual duplication as required by MNT-M2-02.

### 5.2 `mnt_section_click`

Semantic definition:

> An explicit user click on an internal navigational/content-discovery control that does not itself represent contact/conversion intent and does not already have a more specific canonical semantic event.

Examples eligible in the current V1:

- navigation to `#oportunidades`;
- navigation to `#como-escolher`;
- navigation to `#negociacao`;
- the “começar pelo valor” discovery control when it only moves/focuses the catalogue price filter.

Parameters:

```text
section_target = opportunities | how_to_choose | negotiation | top
placement = header_nav | hero | moment_selector | content
funnel_stage = consideration
```

Mutual-exclusion rule:

A click already represented by `mnt_catalog_filter` or `mnt_intent` MUST NOT also emit `mnt_section_click` for the same semantic occurrence.

### 5.3 `mnt_catalog_filter`

Semantic definition:

> An explicit user change to an effective catalogue filter state.

Filter dimensions:

```text
status
zone
price
reset
```

Canonical filter values:

```text
status: all | launch | construction | ready
zone: all | south | west | east
price: all | lte_700k | 700k_1_2m | 1_2m_2m | gt_2m | consult
reset: all
```

Required parameters:

```text
filter_dimension
filter_value
result_count
placement
funnel_stage = consideration
```

Valid placements include:

```text
status_buttons
status_mobile
zone_quick
zone_select
price_select
moment_selector
clear_filters
empty_state_reset
```

Do not emit for:

- initial render/default state;
- programmatic desktop/mobile control synchronization;
- a setter call that does not change effective user state;
- the same user action twice because both UI synchronization and render code ran.

### 5.4 `mnt_catalog_search`

Semantic definition:

> A committed user search-state change inside the development catalogue.

Required parameters:

```text
search_state = active | cleared
result_count
placement = catalog_search
funnel_stage = consideration
```

Privacy/cardinality rule:

**The raw search text MUST NOT be sent to Measurement.**

The current input is free-form and could contain unexpected personal data. Implementation must therefore avoid `search_term`, `query`, raw typed text or equivalent free-form values in the data layer/destinations.

Implementation must also avoid one event per keystroke. Emit only after a bounded committed/debounced search-state change, with exact mechanics defined in MNT-M2-09.

### 5.5 `mnt_intent`

Semantic definition:

> An explicit user action expressing commercial/contact intent before verified lead creation.

Required parameters:

```text
intent_type
contact_channel = form | whatsapp
placement
funnel_stage = intent
```

Project fields are required when a project/offer is selected.

Canonical `intent_type` enum:

```text
request_conditions
project_interest
request_project_conditions
negotiate_scenario
schedule_visit
whatsapp_contact
```

Current V1 mapping contract:

| UI action | `intent_type` | `contact_channel` | `placement` | Project context |
|---|---|---|---|---|
| Header “Receber contato” | `request_conditions` | `form` | `header_nav` | optional/none |
| Hero “Receber condições” | `request_conditions` | `form` | `hero` | optional/none |
| Negotiation “Quero negociar meu cenário” | `negotiate_scenario` | `form` | `negotiation` | optional/none |
| Negotiation “Agendar visita” | `schedule_visit` | `whatsapp` | `negotiation` | optional/none |
| Development card action | `project_interest` | `form` | `catalog_card` | required |
| Selected-project “Quero receber as condições deste Tegra” | `request_project_conditions` | `form` | `interest_context` | required |
| Floating “Receber condições” | `request_conditions` | `form` | `floating` | optional current project context |
| Floating WhatsApp | `whatsapp_contact` | `whatsapp` | `floating` | optional current project context |

Rules:

- UI label changes do not create new event names;
- opening WhatsApp is intent, not verified lead;
- a project card click that only establishes project interest is not `mnt_lead_success`;
- the same click must not also emit `mnt_section_click`.

### 5.6 `mnt_form_start`

Semantic definition:

> The first genuine user interaction with the native Green Form 46 in the current document/form instance.

Required parameters:

```text
form_provider = green
form_id = 46
form_name = MoreEmUmTegra
funnel_stage = intent
placement = form_46
```

Optional project context may be attached when the user arrived with a selected project.

Fire at most once per document/form instance. No field name, field value or typed content is required.

Implementation must observe the native form without intercepting or replacing its Green lifecycle.

### 5.7 `mnt_form_submit_attempt`

Semantic definition:

> A verified observable user submit initiation for native Green Form 46, before the success/failure outcome is known.

Required parameters:

```text
form_provider = green
form_id = 46
form_name = MoreEmUmTegra
funnel_stage = intent
placement = form_46
```

Rules:

- this is **not** a lead event;
- do not preventDefault, duplicate POST, rewrite the action or replace Green submission;
- a mere CTA click or focus is not a submit attempt;
- if Green does not expose a stable non-invasive submit signal, leave this event unimplemented rather than infer it from a weaker signal.

### 5.8 `mnt_lead_success`

Semantic definition:

> One verified successful native Green Form 46 lead registration occurrence.

Required parameters:

```text
form_provider = green
form_id = 46
form_name = MoreEmUmTegra
lead_method = green_form_46
funnel_stage = lead
placement = form_46
```

Optional project context may be attached when a selected project exists.

Hard validity rule:

```text
ONLY VERIFIED FORM 46 SUCCESS -> mnt_lead_success
CTA CLICK -> NOT LEAD
FORM START -> NOT LEAD
SUBMIT ATTEMPT -> NOT LEAD
NETWORK REQUEST START -> NOT LEAD
```

A stable success signal has not been canonically identified by this task. Therefore the event is **DEFINED**, but runtime implementation is gated until MNT-M2-09 can prove a stable, non-invasive Green success signal. If no such signal is available, do not manufacture the event.

## 6. PII / sensitive-data exclusion contract

No MoreNumTegra Measurement event may include, in event parameters or custom dimensions:

- `nome` or any person's name from Form 46;
- email address;
- phone/WhatsApp number entered by the visitor;
- raw form-field values;
- raw free-form catalogue search text;
- free-form message text;
- secrets/tokens;
- a constructed identifier derived from those values merely to make them trackable.

Do not hash PII and treat it as ordinary analytics data under this task. Any future enhanced-conversion/customer-data architecture requires its own explicit privacy/security/attribution decision.

Project names, offer names, controlled filter enums and placement enums are business/content metadata, not visitor PII.

## 7. Cardinality and stability rules

To keep reports usable:

- enum parameters use the allowlists in this contract;
- never use CTA visible text as the canonical `intent_type`;
- never use arbitrary DOM selector/class names as analytics dimensions;
- never encode development name into the event name;
- never encode price as a dynamic event name;
- raw query strings are excluded;
- `mnt_event_id` is a per-occurrence correlation field and must not be registered as a normal high-cardinality reporting dimension unless a later debugging requirement explicitly authorizes that use.

## 8. Consent relationship

The accepted GTM Consent Mode baseline remains:

```text
DEFAULT = denied all four
GREEN Continuar = granted all four
GREEN Cancelar = denied all four

```

This taxonomy defines source semantics, not vendor network behavior.

No second independent consent state machine may be introduced by event instrumentation.

## 9. Destination boundary

No destination event mapping is activated by this taxonomy.

Potential destinations remain separately governed:

```text
GA4 -> MNT-M2-05 + MNT-M2-09
Google Ads conversions -> MNT-M2-04 + later MNT-M6 contracts/gates
Meta Pixel/Dataset/CAPI -> MNT-M2-06 + later authorized implementation
Green -> remains native lead/CRM platform; platform telemetry is not a Measurement adapter
```

The eventual destination may use a vendor-recommended event name different from the canonical source event. That mapping must preserve the source semantic definition.

## 10. Explicit exclusions from taxonomy v1

The following are deliberately not canonical v1 business events:

- raw Green `/page/view`;
- YouTube `qoe`, `playback`, `watchtime`, `log_event` or similar telemetry;
- video autoplay as “engagement”;
- image load/failure;
- MutationObserver execution;
- every DOM click;
- every search keystroke;
- scrolling by itself;
- form-field values;
- page-builder lifecycle noise.

A future user-initiated video event or FAQ/content-depth event may be proposed only if a concrete measurement question justifies the extra instrumentation.

## 11. Implementation source mapping

The current V1 source supports the following future instrumentation attachment points without changing this task into implementation:

- catalogue status/zone/price/search handlers in `src-greenn/moretegra.js`;
- development `data-interest` actions rendered from the governed project data model;
- internal form-bound CTAs in `src-greenn/blocks/01-html-inicial.html` and dynamically generated interest context;
- floating form/WhatsApp actions created by `mountFloatingActions()`;
- native Green Form 46 only through stable, non-invasive lifecycle observation that is proven before implementation.

This mapping is descriptive. No JavaScript/GTM mutation is made by MNT-M2-03.

## 12. QA obligations for later implementation

MNT-M2-09/MNT-M2-10 must prove at minimum:

1. each semantic user occurrence emits no more than one canonical source event of that semantic type;
2. internal programmatic control synchronization does not create duplicate filter events;
3. `mnt_catalog_search` is not emitted on every keystroke and carries no raw query text;
4. project/offer identity matches the governed data model when present;
5. WhatsApp/form intents are not counted as leads;
6. `mnt_form_start` fires at most once per document/form instance;
7. `mnt_form_submit_attempt` requires a real observable submit initiation;
8. `mnt_lead_success` requires a proven Green success signal and occurs once per accepted lead occurrence;
9. no visitor PII is exposed in dataLayer event parameters;
10. canonical-host and Consent Mode controls from MNT-M2-02 remain intact.
